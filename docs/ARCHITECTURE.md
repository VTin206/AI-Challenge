# Architecture

## Pipeline

`JSONL input → package discovery → ingestion → schema catalog → business-rule context → Vietnamese intent/time analysis → planner → SQL validator → bounded SQLite execution → result checks → JSONL formatter`

Each stage has a small Python interface. CSV, XLSX and SQLite readers produce the same `DataTable` representation. The SQLite query engine is the execution backend; an optional local OpenAI-compatible planner can be substituted without changing ingestion or execution.

## Trust and precision boundaries

- Source files are read only. Source SQLite is opened with `mode=ro`; imported tabular data is copied into an in-memory SQLite database.
- Identifiers are normalized for internal use while original names are retained in the catalog. Only strict, unambiguous integer/decimal strings are inferred as numbers; ambiguous locale formats remain text.
- The SQL authorizer rejects mutations, schema inspection, attachment, pragmas, unknown tables and dangerous file/extension functions. `execute()` accepts one statement, applies VM-step/time limits, and caps result rows.
- Decimal aggregates use Python `Decimal` through registered SQLite aggregate functions. SQL generated by the baseline uses these helpers when aggregating.
- The SQL engine verifies execution safety, not whether a join or business interpretation is semantically correct. The result validator abstains when ambiguity is detected.

## Business context and precedence

README and rulebook text is retained with source provenance. Executable directives support an explicit numeric priority. A higher priority wins; conflicting rules at the same highest priority remain unresolved and cause abstention for dependent questions. This is an implementation policy, not confirmed competition precedence; replace it if official rules specify another order.

## Temporal handling

Relative solar dates are computed from the question's `as_of_date`, using Monday-first weeks and half-open SQL ranges `[start, end)`. Ambiguous date strings are not guessed. Lunar expressions remain unsupported until the official calendar schema is available.

## LLM boundary

The optional planner sends only the question, compact schema, rule text, and as-of date to the configured endpoint. Local Ollama-compatible endpoints are supported; default behavior makes no network request. LLM output is treated as untrusted SQL and runs through the same authorizer and query limits as rule-based SQL.
